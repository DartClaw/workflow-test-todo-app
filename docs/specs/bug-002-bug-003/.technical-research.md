### S02 - Apply quick-add default priority

Primary files:
- `src/app/routes/todos.py:73-132` - `create_todo(...)` is the quick-add entry point and currently omits any explicit priority assignment.
- `src/app/database.py:65-84` - `Todo.priority` has no database-level default, so route-level creation behavior currently determines whether new rows are initialized correctly.
- `src/app/templates/partials/todo_item.html:1-32` - row markup and badge styling read `todo.priority` directly and should reflect the stored default immediately.
- `src/app/static/js/app.js:111-124` - reopen flow reads `data-todo-priority` into the edit dialog selector.
- `tests/test_todos.py:13-30` - existing create test already asserts `created.priority == "low"` and is the natural place to expand regression coverage around rendered response content.

Notes:
- This story can stay narrowly focused on quick-add creation and the first reopen path. Later priority edits are already handled by `update_todo(...)` and only need regression coverage to prove the default does not block explicit changes.

## Shared Architectural Decisions

1. Keep both fixes inside the existing HTMX-first HTML partial workflow.
   - Routes continue to return `templates.TemplateResponse(...)` fragments and `partials/error.html` for validation failures.

2. Preserve existing auth, ownership, and title-validation behavior.
   - Neither defect requires changes to session handling, ownership checks, or unrelated todo fields.

3. Treat the due-date round-trip contract as date-only.
   - The edit dialog uses `type="date"` and row rehydration already serializes values through `format_date_input(...)`, so spec work should align parsing and rendering to that contract rather than introducing time-of-day semantics.

4. Establish the quick-add default priority at creation time.
   - The created `Todo` should already carry the canonical `low` value before the response fragment is rendered, rather than relying on the edit dialog's default UI state.

5. Prove behavior at both persistence and UI boundaries.
   - Regression coverage should check stored database state plus returned HTML that drives reopen behavior (`data-*` attributes, visible badge/date output, and clear/error flows where applicable).
