# BUG-001 - Sidebar Incomplete Count Updates After Todo Delete

## Feature Overview and Goal
Deleting a Todo must update the active `TodoList` incomplete-count badge immediately, without requiring a full page reload. This aligns the delete flow with the existing HTMX OOB swap behavior already used by todo creation and completion toggles.

Example: toggling a todo updates both the todo row and the sidebar's incomplete-count badge in a single response. Before adding a new interaction, check whether it needs an OOB swap.

## Scenarios

### Delete Incomplete Todo Updates Sidebar Count
- **Given** a `TodoList` with two incomplete `Todo` items and the sidebar badge showing `2`
- **When** the user deletes one of those incomplete Todos
- **Then** the delete response includes an HTMX OOB swap for `list-{list_id}-count` and the rendered count becomes `1`

### Delete Last Incomplete Todo Reaches Zero
- **Given** a `TodoList` with exactly one incomplete `Todo` and the sidebar badge showing `1`
- **When** the user deletes that Todo
- **Then** the delete response still includes the OOB swap and the rendered count becomes `0`

### Delete Completed Todo Leaves Incomplete Count Unchanged
- **Given** a `TodoList` with one completed `Todo`, one incomplete `Todo`, and the sidebar badge showing `1`
- **When** the user deletes the completed Todo
- **Then** the delete response includes the OOB swap and the rendered count remains `1`

### Delete Missing Todo Returns Existing Error Behavior
- **Given** a delete request for a `Todo` id that does not exist
- **When** the request hits `/api/todos/{todo_id}`
- **Then** the route preserves its current non-success response behavior and does not emit a misleading sidebar count update


## Scope & Boundaries

### In Scope
- The `delete_todo` route response contract for authenticated HTMX deletes.
- Reuse of the existing incomplete-count calculation and sidebar badge target id for delete responses.
- Automated regression coverage for the delete response markup and rendered count value.

### What We're NOT Doing
- Changing create or toggle handlers - they already follow the intended OOB swap pattern.
- Refactoring shared count-rendering infrastructure across routes - BUG-001 only needs the existing pattern applied to delete.
- Changing authentication, authorization, or delete status-code semantics - those are outside this defect's scope.
- Altering sidebar layout or badge styling - the issue is stale data, not presentation.


## Architecture Decision

**We will**: make `delete_todo` return an HTML partial carrying the sidebar badge OOB swap, using the same incomplete-count helper and DOM id pattern already used elsewhere -- this is the smallest change that matches the repo's HTMX-first architecture (over introducing JSON or client-side count bookkeeping).


## Technical Overview

### UI/UX Design
The visible behavior change is limited to the sidebar badge staying in sync immediately after a delete action. No new UI controls or flows are introduced.

### Integration Points
The delete route must keep cooperating with HTMX row removal while also returning a fragment that updates `#list-{list_id}-count` out of band.

## Constraints & Gotchas
- **Constraint**: This app returns server-rendered HTML fragments, not JSON -- Workaround: keep the delete response as a `TemplateResponse` partial rather than inventing client-side badge updates.
- **Avoid**: Recomputing the count before the delete commit -- Instead: delete first, commit, then derive the remaining incomplete count from persisted state.
- **Critical**: The sidebar badge target id must stay `list-{list_id}-count` -- Must handle by: reusing the existing badge id convention so the OOB swap reaches the correct `TodoList`.
