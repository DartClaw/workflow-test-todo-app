- `src/app/templates/app.html:121-156` - The edit dialog uses `name="due_date"` with `type="date"`, so the browser/control contract is date-only and blank string on clear.

- `src/app/templates/partials/todo_item.html:1-40` - The todo row stores `data-todo-due-date="{{ format_date_input(todo.due_date) }}"`, renders the visible date badge, and passes the same formatted value into the edit dialog click handler.

- `tests/test_todos.py:44-62` - Existing update coverage proves title/note/priority updates and a successful due-date assignment path, but it does not assert clear behavior, invalid-format rejection, or reopen metadata consistency.

## Shared Architectural Decisions

1. **HTMX error contract stays intact**
   - Both stories keep the existing HTML-fragment contract. Successful operations continue returning todo-row partials. Validation failures return `partials/error.html` with a visible message.
   - This applies directly to BUG-002 invalid-date handling and indirectly to BUG-003 because quick-add remains a single HTMX POST.

2. **Date-only edit-dialog payload is authoritative**
   - The edit dialog control is `type="date"`, and reopen behavior already uses `format_date_input()` to round-trip `YYYY-MM-DD`. The update route should align with that existing contract instead of inventing a datetime-specific alternative.

3. **Default priority must be enforced at persistence time**
   - The canonical default is `low`, already expressed in the PRD and Pydantic model defaults. The durable fix is to apply that default in quick-add creation before commit rather than hiding missing data with UI-only fallbacks.

4. **Thin-story independence is preserved by sequencing, not merging**
   - The PRD explicitly requires BUG-002 and BUG-003 to remain separate thin stories. They are functionally independent, but they share `src/app/routes/todos.py` and `tests/test_todos.py`, so the plan sequences them by phase to avoid needless conflicts while preserving separate specs.
